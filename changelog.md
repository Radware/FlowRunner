## Unreleased — Per-step assertions + run test-summary (UX Wave 3, lane assertions)
- **Decision:** added an **additive optional** `step.assertions` = `[{ target, operator, value, critical? }]` on **request** steps. Each assertion is checked against the step's result **after** it runs and **NEVER changes request execution** — it only annotates the result and (optionally, per a `critical` flag) requests a stop. **Targets:** `status`, `duration` (ms), `headers.<name>`, `body.<path>` (dotted/array paths). **Operators reuse the frozen `conditionData` vocabulary** — evaluation goes through the existing `evaluateCondition` + `evaluatePath` (in `executionHelpers.js`), so the CLI can evaluate the same files with its existing operator set (cross-app safe). **Why:** highest-value new capability that reuses existing engine data, stays additive, and needs no new JS engine on the Python side.
- **Evaluation (`executionHelpers.js`):** new pure `evaluateAssertions(assertions, output, durationMs)` → a test-summary `{ total, passed, failed, allPassed, criticalFailed, results[] }`, plus `buildAssertionSubject(output, durationMs)`. **Subject/path subtlety:** `evaluatePath` dives into `data.body` for prefix-less paths, so bare `status`/`duration` are evaluated against a **body-less mini-subject** (see `resolveAssertionTarget`) while `headers.*`/`body.*` use the full subject — this is the one non-obvious bit. Unknown/newer operators degrade to a **failed** assertion (never throw), matching the tolerant-reader stance; a genuine eval error is caught and reported as failed, never aborting the run.
- **Runner wiring (`flowRunner.js`):** `_executeRequestStep` now stamps an additive `duration` (ms) onto the request `output`. `_executeSingleStepLogic` calls `_evaluateStepAssertions(step, result)` after a request (only when it produced output), attaching `result.assertionSummary`. A failed **critical** assertion triggers `stop()` (the ONLY way an assertion affects control flow); non-critical failures are non-blocking. The evaluator is **injected** as `evaluateAssertionsFn` (defaulted in `createFlowRunner`) to avoid a `flowRunner`→`executionHelpers` import cycle — an unset evaluator = identical legacy behavior (existing `new FlowRunner({...})` call sites, incl. the test harness, don't evaluate assertions).
- **Encoding (`flowCore.js`):** `flowModelToJson`/`jsonToFlowModel` carry `step.assertions` verbatim (deep-copied), **only when non-empty** — a step without assertions never gains an empty key, keeping golden pre-sprint flows byte-stable. `goldenOldFlow.test.js` stays green (10/10).
- **UI:** Power-mode **Assertions tab** in the request inspector (`flowStepComponents.js`, `setupAssertionsEditor`) — target/operator/value/critical rows; valueless operators (`exists`, `is_empty`, …) hide the value field; string values are coerced to number/bool/null on save (`status` "200" → `200`). Runner panel shows **per-step PASS/FAIL rows + a header badge** and an **aggregate test-summary panel** (`renderTestSummaryPanel`, hidden when a run defined no assertions). `styles.css` `/* === WAVE3 assertions === */` block consumes **semantic tokens only** (`--run-success`, `--run-error`, `--surface-raised/-sunken`, `--text-muted`, `--border`, `--accent-contrast`) — no hardcoded colors.
- **Cross-app:** `.flow.json` change is **additive**; `flowrunner-cli` (Python) must evaluate `step.assertions` with the same operator vocabulary (cross-repo-cli lane) — until then an older CLI **ignores** the field (`extra='ignore'`), which is safe. Reconcile the row shape with the ShowRunner portal's `step.assertions[]` when that shape is documented; the current `{ target, operator, value, critical? }` is the FlowRunner encoding.
- **Scope/ownership:** edited `executionHelpers.js`, `flowRunner.js`, `flowCore.js`, `flowStepComponents.js`, `runnerInterface.js`, shared `styles.css` (delimited block) + shared `index.html` (one additive `#runner-test-summary` node). **No new JS modules → no `build.files` change** (all edited modules already listed). No new deps. TDD: `__tests__/assertions.test.js` (16), `flowRunnerAssertions.test.js` (6), `assertionsEditor.test.js` (7), `testSummaryPanel.test.js` (7). Suite: 397 baseline → **433 passing**.
## Unreleased — React Flow island as a flag-gated alternative visualizer (UX Wave 3, lane react-island)
- **Decision:** landed a production **React Flow island** (`@xyflow/react`, built by Vite) as a **flag-gated, off-by-default** alternative node-graph engine, per `docs/engine-decision.md` (React Flow scored best; the wave2 spike proved a `base:''` Vite build emits a single same-origin script, CSP-clean under `script-src 'self'`). **Drawflow (`flowVisualizer.js`) remains the DEFAULT and is untouched.** **Why now:** the spike retired the CSP risk; shipping the island present-but-inactive lets us dogfood the React engine behind a flag without any risk to the default path or the packaged build.
- **Two-part structure.** (1) `visualizer-island/` — a self-contained Vite/React app with its **own `package.json`** (react/react-dom/@xyflow/react/vite) that builds a single **IIFE** bundle to `assets/visualizer-island/island.js` + `island.css` via `base:''` + lib mode. The bundle assigns a global `FlowRunnerReactIsland.createReactFlowVisualizer(mount, options)`. Verified CSP-clean: **0** `eval(`/`new Function`/`importScripts`/`document.write`/`blob:`/`Worker`. (2) `reactFlowVisualizer.js` — a **plain-JS facade class `ReactFlowVisualizer`** (no React import) that the app can `new` **identically** to Drawflow. It loads the island as a same-origin `<script>` + `<link>`, **queues** contract calls issued before the async bundle mounts and **flushes them in order**, then delegates. Honors the **entire** FlowVisualizer contract (`docs/visualizer-contract.md`: 13 core methods + `applyLayout`/`undoLayout`/`canUndoLayout`/`jumpToNextError` + 7 callbacks).
- **Engine selection seam (additive):** `app.js → initializeVisualizer()` now calls `selectVisualizerEngine()`, which returns `ReactFlowVisualizer` **only** when `localStorage['flowrunner.visualizerEngine'] === 'react'` and falls back to Drawflow on any error. Default OFF. Both engines get the same callbacks, so every downstream call site is unchanged.
- **Packaging:** `build:island` (installs the island's own deps + `vite build`) runs via `prebuild`/`predist`/`prepack` hooks, so `npm run dist` rebuilds the island before `electron-builder`. Added `reactFlowVisualizer.js` + `assets/visualizer-island/**/*` to `build.files` (the #1 rule). Island build deps also listed as **root devDependencies** so the CI packaged-build gate resolves them. Built assets are gitignored (regenerated by the hook).

## Unreleased — Per-request retries/backoff + cURL/HAR import (UX Wave 2, lane engine-features)
- **Decision (retries):** `_executeRequestStep` in `flowRunner.js` now honors an **additive** request-step field `step.retries = { count, delayMs }`. A retry fires on a **non-2xx HTTP status OR a network/fetch error**, up to `count` times, sleeping `delayMs` (via the existing `_sleep`, which short-circuits on `stopRequested`) between attempts. Each attempt gets a **fresh `AbortController` + 30s timeout** (an aborted/timed-out controller can't be reused). **Why:** transient upstream failures are common in live demos; a bounded retry avoids a whole-flow stop on a blip. Default is `count: 0`, which is **byte-for-byte the previous single-attempt behavior** — the `onFailure` (`stop`/`continue`) semantics are unchanged and only apply once retries are exhausted. A **user-requested stop/abort is never retried**. CROSS-REPO FOLLOW-UP: `step.retries` is additive in `.flow.json`; flowrunner-cli (Python) must eventually honor it (until then it's ignored, which is safe).
- **Decision (import):** new **zero-dependency** module `importCurlHar.js` — `parseCurl(str)` → one request step, `parseHar(objOrJson)` → request steps (one per http(s) entry).
